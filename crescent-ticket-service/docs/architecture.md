# Architecture - Crescent Motors Ticket Service (Microservice 2, Version 1)

## 1. Context

```
                         (future)                                   Version 1
 Customer --WhatsApp--> [WhatsApp Webhook Service] --REST + key-->  [Ticket Service] --SQL--> [PGlite / Supabase]
                         Microservice 1, not built                   this repository
 Support tools / Swagger / Postman / curl -------------REST + key-->      ^
```

Version 1 is the ticket service only. It is fully usable on its own through
REST; `POST /api/v1/intake/messages` is the seam where the future WhatsApp
service will plug in.

## 2. Layers

| Layer | Location | Responsibility |
|---|---|---|
| HTTP routes | `app/api/` | Paths, status codes, OpenAPI docs, dependency wiring. No business rules. |
| Schemas | `app/schemas/` | Pydantic request validation (unknown fields rejected, strings trimmed, phone/email normalization) and response models (timestamps forced to UTC). |
| Services | `app/services/` | Business rules, status transitions, event recording, idempotency. Each public command is **one transaction**: it commits once or not at all. |
| Repositories | `app/repositories/` | SQLAlchemy queries only (bound parameters; no SQL string building with user input). |
| Models | `app/models/` | ORM mapping, constraints, indexes; mirrored exactly by the Alembic migrations. |
| Core | `app/core/` | Settings, engine/session factory, API-key check, error model and exception handlers. |

Request flow: `route -> Depends(require_api_key) -> Depends(get_session) ->
Depends(get_current_company) -> service -> repositories -> commit -> response
model`. The per-request session is always closed, which rolls back anything a
service did not commit (for example when an exception is raised mid-way).

### Error model

Every error response is `{"error": {"code", "message", "details"}}`.
Domain errors (`AppError`) carry a stable `code`. Validation errors list
`loc/msg/type` only, never the submitted value. Database connectivity failures
become `503 DATABASE_UNAVAILABLE`, a missing schema becomes `503
DATABASE_NOT_MIGRATED`, unexpected unique/foreign-key violations become `409
CONFLICT`, and anything else (including CHECK violations, which indicate a bug)
becomes `500 INTERNAL_ERROR` with the details only in the server log.

### Security

- `X-API-Key` on every `/api/v1` route, compared with `secrets.compare_digest`.
  The key comes from `API_KEY`; placeholders and short keys are refused at startup.
- Keys and database passwords are `SecretStr` (masked in reprs); headers are never logged.
- `DATABASE_URL` to a non-local host must use `sslmode=require|verify-ca|verify-full`.
- The PGlite server refuses to bind to anything but `127.0.0.1`, `::1` or `localhost`.
- `/health` and `/health/ready` are public but return no data beyond status words.
- This is an internal-service safeguard, **not** user authentication (no users,
  roles, rotation or rate limiting).

## 3. Data model

```
companies 1---* customers 1---* tickets *---0..1 agents *---1 companies
                                  |
                                  +---* ticket_messages
                                  +---* ticket_events
```

Integrity rules implemented in the database (not only in code):

| Rule | Implementation |
|---|---|
| No duplicate customer per company + normalized phone | `uq_customers_company_id_phone_number` |
| No duplicate agent email per company | `uq_agents_company_id_email` (emails stored lower-case) |
| Ticket customer and agent belong to the ticket's company | composite FKs `fk_tickets_customer_company`, `fk_tickets_agent_company` -> `(id, company_id)` |
| One active ticket per customer | partial unique index `uq_tickets_one_active_per_customer ON tickets(customer_id) WHERE status IN ('OPEN','IN_PROGRESS')` |
| `resolved_at` set exactly when RESOLVED | `ck_tickets_resolved_at_matches_status` |
| Valid status / priority / sender / source / event values | CHECK constraints (VARCHAR, not PG enums, so values can be added by a simple migration) |
| An external message is processed once per company and source | partial unique index `uq_ticket_messages_company_source_external_id` |
| Messages belong to the same company as their ticket | composite FK `fk_ticket_messages_ticket_company` |

`ticket_messages.company_id` is an addition to the requested field list: a
unique index cannot reach the company through a join, and the specification
asks for duplicate detection "within the appropriate source and company scope".

Timestamps are `timestamptz`, generated by the application with microsecond
precision (`created_at` and `updated_at` get the same instant on insert); the
database also has `now()` defaults for rows inserted by hand.

Migrations: `0001` creates the schema, `0002` seeds Crescent Motors with a
fixed UUID (`c2e5c3a0-7d1b-4b5e-9a6f-1c0de5c00001`). A test runs `alembic check`
so the models and migrations cannot drift apart.

## 4. Key behaviours

**Status transitions** (`app/services/ticket_service.py`, `ALLOWED_TRANSITIONS`):
`OPEN -> IN_PROGRESS -> RESOLVED`. Assignment of an active agent moves `OPEN`
to `IN_PROGRESS`. Every change writes `ticket_events` in the same transaction.
Ticket rows are read with `SELECT ... FOR UPDATE` before changes.

**Intake** (`app/services/intake_service.py`): one transaction that (1) returns
the original result if the `external_message_id` was already processed, (2)
finds or creates the customer, (3) reuses the active ticket or creates one with
its `TICKET_CREATED` event, (4) inserts the message. If a unique constraint fires
because of a concurrent request (same phone, same active ticket, same external
id), the transaction is rolled back and processed once more, which then sees
the other request's committed rows. A test forces this path.

## 5. Database: PGlite locally

`database/start-db.mjs` (Node.js 22) opens a persistent PGlite data directory
and serves it with `PGLiteSocketServer` from `@electric-sql/pglite-socket`.
It binds to loopback only, takes a lock file (`<data-dir>.lock`) so two
processes can never open the same directory, and on `SIGINT`/`SIGTERM`/`SIGHUP`
(or stdin closing, used by the tests) stops the socket server and closes the
database cleanly.

The Python side uses SQLAlchemy 2.0 with **psycopg2** and a pool of size 1
(`DB_POOL_SIZE=1`, `DB_MAX_OVERFLOW=0`), `pool_pre_ping` (transparent
reconnection after a database restart, covered by a test) and
`sslmode=disable` for the local server.

### PGlite: verified behaviour and limitations

Each item below was observed on this project's pinned versions
(PGlite 0.5.8 = PostgreSQL 18.3, pglite-socket 0.2.11), most of them by
automated tests; the rest during development as noted.

| # | Behaviour | Consequence / handling |
|---|---|---|
| 1 | PGlite is single-connection. The socket server multiplexes clients and executes **one wire message at a time**; while a client is inside a transaction, other clients' queries wait (no timeout) until it commits or rolls back. Verified with two threads: B's read waited for A's commit. | Keep transactions short; pool size 1; never leave a `psql` session inside `BEGIN`. |
| 2 | `--max-connections` (default 1 in the package, **4** in `start-db.mjs`). Extra clients receive the plain text `Too many connections` and are disconnected (psycopg2 reports an `OperationalError`). | Mapped to `503 DATABASE_UNAVAILABLE`. 4 allows API + Alembic + seed/smoke/psql at once. |
| 3 | No TLS: the server answers `N` to the SSL request; `sslmode=prefer` falls back, `require` fails. | Local URL uses `sslmode=disable`; server bound to localhost. |
| 4 | Startup parameters are ignored (`options=-c timezone=UTC` had no effect). The session time zone follows the host (an IST host reported `Etc/GMT-5`). Stored instants are correct. | API serializes every timestamp in UTC; application generates timestamps itself. |
| 5 | User name, password and database name are ignored: one server = one database. | Test isolation uses a **separate server process, data directory and port**. |
| 6 | **psycopg 3.3.6 is incompatible**: after any server error it fails with `received 0 results from command 'ROLLBACK'`. psycopg2 2.9.13 passed all probes (errors, rollback, constraints, concurrency). | psycopg2 is the driver. |
| 7 | `CancelRequest` is silently ignored by the socket server. | Query cancellation / client-side statement timeouts do not interrupt PGlite. |
| 8 | `now()` has millisecond resolution in PGlite. | Application timestamps (microseconds) are used for ordering. |
| 9 | A hard kill (no clean shutdown) did not lose committed data in a test (500 rows recovered through WAL replay); the stale lock is cleaned up on the next start. | Still stop with `Ctrl+C`. |
| 10 | Creating a fresh data directory takes about 3 s on Linux (ext4) but 20-30 s on a Windows NTFS drive; the full test suite takes about 25 s on Linux and 70 s on Windows. | One-time cost per data directory. |
| 11 | `SELECT ... FOR UPDATE` works but has no practical effect (transactions are already serialized). | Row locking is only meaningful on PostgreSQL/Supabase - see migration testing below. |

No PostgreSQL extensions are used; `gen_random_uuid()` appears only in a test.

## 6. Future extension: WhatsApp Webhook Service (not implemented)

A separate microservice would:

1. Expose the Meta webhook (verification challenge, `X-Hub-Signature-256`
   validation with the app secret) and return `200` quickly.
2. Map each inbound message to the intake contract:
   `phone_number = "+" + wa_id`, `customer_name = contacts[0].profile.name`,
   `message_text = text.body`, `external_message_id = messages[0].id` (the `wamid`).
3. Call `POST /api/v1/intake/messages` with its own API key. Meta delivers
   webhooks **at least once**; the existing `external_message_id` idempotency
   makes retries safe (`200` + `"duplicate": true`).

Changes needed in this service when that happens:

- Add `WHATSAPP` to `MessageSource` and the `ck_ticket_messages_source_valid`
  CHECK (new Alembic migration), and let the intake request (or the caller's
  API key) choose the source. Duplicate detection is already scoped by source.
- Outbound replies: record agent messages in an outbox table in the same
  transaction and let the WhatsApp service deliver them (no direct calls to
  Meta from the ticket service); add delivery-status updates.
- Per-service API keys (or mTLS / signed service tokens) instead of one shared key.
- Media messages, templates and the 24-hour customer service window rules.

## 7. Future extension: Supabase PostgreSQL (not implemented)

What should work unchanged: models, migrations, repositories and services use
standard PostgreSQL features only (UUID, timestamptz, CHECK, partial unique
indexes, composite foreign keys, `ON CONFLICT DO NOTHING` in the seed).
Switching is a configuration change:

```
DATABASE_URL=postgresql+psycopg2://<user>:<password>@<host>:5432/postgres?sslmode=require
DB_POOL_SIZE=5
DB_MAX_OVERFLOW=5
```

The service refuses a non-local URL without `sslmode=require/verify-ca/verify-full`.

**PGlite and Supabase are not identical. Before going live, test:**

- [ ] `alembic upgrade head` on an empty Supabase project/branch (never production first), then the full `pytest` suite pointed at a **separate** Supabase test database (the harness currently starts PGlite; add a `DATABASE_URL` override for this).
- [ ] Real concurrency: row locks (`FOR UPDATE`), the intake retry on unique violations, and simultaneous assignment/resolution, which PGlite serializes and therefore never exercises.
- [ ] Connection pooling: Supavisor *transaction* mode does not keep session state; psycopg2 does not use server-side prepared statements, but verify. Choose pool sizes against the Supabase plan's connection limit.
- [ ] TLS with `sslmode=verify-full` and the Supabase CA certificate.
- [ ] Time zone: Supabase sessions use UTC (PGlite uses the host offset); the API already normalizes to UTC.
- [ ] **Row Level Security / Data API exposure**: tables in Supabase's `public` schema are reachable through the auto-generated REST API. Either enable RLS on all six tables (with no anon policies) or create them in a non-exposed schema, so customer data is only reachable through this service.
- [ ] Driver: consider `psycopg2` built from source (recommended by the psycopg project for production) or re-evaluate psycopg 3, which works with real PostgreSQL.
- [ ] Backups, point-in-time recovery and secret management for `DATABASE_URL` and `API_KEY`.
